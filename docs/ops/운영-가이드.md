# 운영 가이드 — 수동 배포

> 배포 방식: **수동 배포**. CI(`.github/workflows/ci.yml`)는 빌드+테스트 후 GHCR 이미지 push까지만 자동화한다.
> CD 자동화는 범위 외(수동 유지가 결정 사항). 운영 서버(EC2)·운영 DB(RDS)는 사용자가 직접 관리한다.
> 마지막 갱신: 2026-11-09

## 준비 상태 체크리스트

- [x] Dockerfile
- [x] docker-compose.yml / docker-compose.prod.yml
- [x] CI: 빌드+테스트 → GHCR push (amd64 단일 플랫폼)
- [x] prod 프로파일
- [x] DB DDL (`docs/db/db-schema.sql`, 사용자가 RDS에 직접 적용)

## 배포 전 확인

1. **DB 스키마**: 첫 배포는 RDS에 `docs/db/db-schema.sql` 실행. 이후 스키마 변경은 `docs/db/db-schema.md` 변경 이력의 `ALTER`를
   먼저 적용한다. 앱은 스키마를 만들지 않으므로(`ddl-auto: validate`) 미적용이면 기동 시 `Schema-validation` 실패.
2. **iOS 앱 호환**: 2026-09-03 응답 봉투(`ApiResponse`: success/data/error/message) 도입으로 모든 엔드포인트의 바디 최상위
   구조가 바뀌었다. iOS 앱 디코더가 갱신되기 전에는 운영 배포를 미룬다(계약은 README "공통 응답 구조").
   2026-09-06 `PUT /api/settings`에 `notifications` 객체(cutoff·bedtimeResidual·recordReminder, 전부 필수)가 추가되어
   갱신 전 iOS 빌드의 설정 저장은 400 `VALIDATION_FAILED`를 받는다.
   2026-11-01 리프레시 토큰 JWT 전환으로 배포 시 기존 리프레시 토큰이 모두 무효가 되어 전 사용자가 한 번 다시 로그인한다.
   2026-11-03 로그인에 429 `TOO_MANY_LOGIN_ATTEMPTS`(같은 이메일 15분 내 5회 실패)가 추가됐다. 봉투 구조는 같아 디코딩은
   그대로 되지만, 앱이 로그인 실패를 401로만 가정하면 서버 `message`를 그대로 보여 주는지 확인한다.
3. **CI 통과**: main의 최신 CI가 녹색이고 GHCR에 `latest` 이미지가 올라갔는지 확인.
4. **E2E 통과**: PC에서 `./gradlew e2eTest`. 운영과 같은 `prod` 프로파일·실제 MySQL·실제 이미지로 가입→학습→로그아웃을 돌린다.
   H2 통합 테스트가 못 잡는 문자셋·collation·DDL 문제가 여기서 드러난다(Docker 필요, 수 분 소요).

## 수동 배포 절차

EC2는 외부 인터넷이 없어 `docker compose pull`이 불가하다. PC에서 이미지를 받아 파일로 옮긴다.

```bash
# 1. PC: GHCR 로그인 (이미지가 private)
gh auth refresh -s read:packages
gh auth token | docker login ghcr.io -u ksiksit --password-stdin

# 2. PC: 이미지 pull + 파일로 저장 (CI는 amd64만 빌드 — Apple Silicon에서는 platform 명시)
docker pull --platform linux/amd64 ghcr.io/ksiksit/caffeine_tracker_server:latest
docker save -o caffeine-app.tar ghcr.io/ksiksit/caffeine_tracker_server:latest

# 3. PC → EC2 전송
scp caffeine-app.tar <ec2-user>@<ec2-host>:~/

# 4. EC2: 이미지 로드 후 기동 (Alertmanager 를 켰다면 먼저 배포 사일런스 — "경보" 절)
docker load -i caffeine-app.tar
docker compose -f docker-compose.prod.yml up -d

# 5. EC2: 헬스 확인
curl localhost:8081/actuator/health   # {"status":"UP"} 이면 성공

# 6. PC: 스모크 E2E — SSH 터널로 EC2:8080 을 PC:18081 로 연결한 뒤 읽기 위주 시나리오 실행
ssh -N -L 18081:localhost:8080 <ec2-user>@<ec2-host> &
E2E_EMAIL=<전용 계정> E2E_PASSWORD=<비밀번호> ./gradlew e2eTest -Pe2e.baseUrl=http://localhost:18081
kill %1   # 터널 종료
```

스모크 전용 계정은 운영에 한 번만 가입 API로 만들어 두고, 자격증명은 레포·스크립트에 저장하지 않는다.
`-Pe2e.baseUrl`이 있으면 쓰기 시나리오(가입·기록·학습)는 건너뛰고 로그인·조회·토큰 재발급만 확인한다. 터널은 API 포트만 연결하므로 헬스는 5단계에서 확인한다.

EC2 홈(`~`)에 `docker-compose.prod.yml`, `monitoring/` 폴더, `.env`(`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`,
`GRAFANA_ADMIN_PASSWORD`)를 같은 폴더에 둔다. compose가 같은 폴더의 `.env`를 자동 로드하고, `monitoring/`의 설정 파일을
상대 경로로 마운트한다. 위 절차는 앱 이미지만 옮긴다 — Prometheus·Grafana를 처음 올리거나 버전·설정을 바꿀 때는
아래 "Prometheus·Grafana 설치" 절차를 먼저 한다. 이미지가 EC2에 없으면 `up -d`가 pull을 시도하다 실패한다.

## 메트릭과 로그

운영 프로파일에서 헬스·메트릭은 관리 포트 8081에서만 응답하고 8080에서는 404다. compose는 8081을 EC2 루프백에만
바인딩하므로 EC2 안에서 조회한다. 보안 그룹이나 compose에서 8081을 외부로 열지 않는다 — 인증 없이 응답하는 포트다.

```bash
# EC2: Prometheus 형식 메트릭 (HTTP 요청, JVM, Hikari 등)
curl localhost:8081/actuator/prometheus

# EC2: 5xx 요청 찾기. 로그는 JSON 한 줄이고 requestId·userId 필드가 함께 나간다
docker logs caffeine-app 2>&1 | grep 'status=5'

# EC2: 한 요청의 로그 전부 보기
docker logs caffeine-app 2>&1 | grep '<requestId>'
```

로그는 컨테이너당 10MB × 5개까지만 보관하므로 오래된 로그는 사라진다.

### Prometheus·Grafana

`docker-compose.prod.yml`이 앱과 함께 Prometheus와 Grafana를 띄운다. Prometheus가 `app:8081/actuator/prometheus`를
15초마다 긁어 15일(또는 2GB)까지 쌓고, Grafana가 "카페인 트래커 서버" 대시보드로 보여 준다. 데이터소스와 대시보드는
`monitoring/grafana/`에서 기동 때 자동 등록된다. 두 포트(9090·3000)도 인증이 약하거나 없으므로 루프백에만 바인딩하고
PC에서는 SSH 터널로 본다.

```bash
# PC: Grafana(3000)·Prometheus(9090) 터널. 브라우저로 http://localhost:3000 → admin / GRAFANA_ADMIN_PASSWORD
ssh -N -L 3000:localhost:3000 -L 9090:localhost:9090 <ec2-user>@<ec2-host>

# EC2: 수집 대상 상태 — "health":"up" 이면 앱 메트릭을 긁고 있다
curl -s localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"'
```

대시보드 패널: 수집 상태·5xx 비율·p95 지연·초당 요청(상단), 엔드포인트별 요청·p95, 상태 코드별 요청, ERROR·WARN 로그 수,
JVM 힙, DB 커넥션 풀, CPU, 그리고 아래 도메인 메트릭 4개(학습 실행·학습 밤별·수면 업로드·로그인, 최근 1시간 합계).
5xx나 지연이 튀면 그 시각의 로그를 `docker logs --since`로 보고 `requestId`로 좁힌다.
p95는 `application-prod.yaml`의 지연 버킷(25ms~5s 8개) 사이를 보간한 근삿값이다.

#### 도메인 메트릭

HTTP 메트릭은 상태 코드까지만 보인다. 학습 run 은 건너뛰어도 200, 수면 업로드는 중복이 섞여도 200, 로그인 실패는 이메일이
없든 비밀번호가 틀리든 같은 401 이라, 서비스가 실제로 한 일은 아래 카운터로 본다. 모두 기동 때 0으로 등록되고,
사용자 식별자는 태그로 붙이지 않는다(사용자 수만큼 시계열이 늘어난다). 메트릭은 관리 포트(8081)에서만 나간다.

| 메트릭 (Prometheus 이름) | 태그 | 1 오르는 때 |
|---|---|---|
| `caffeine_learning_runs_total` | `outcome` = `LEARNED` 또는 skip 사유 | 학습 실행 1회. 1밤 이상 학습했으면 `LEARNED`, 아니면 응답 `skipReason`과 같은 값 |
| `caffeine_learning_nights_total` | `outcome` = `LEARNED` 또는 밤 단위 skip 사유 | 실행이 살펴본 후보 밤 1개. `LEARNING_DISABLED`·`NO_SLEEP_SUMMARY`는 실행 전체 사유라 여기 없다 |
| `caffeine_sleep_samples_total` | `result` = `inserted`·`duplicate` | 업로드된 샘플 1개. `duplicate` = 이미 저장됐거나 같은 배치 안에서 겹친 샘플(응답 `received - inserted`) |
| `caffeine_auth_logins_total` | `outcome` = `SUCCESS`·`WRONG_PASSWORD`·`UNKNOWN_EMAIL` | 비밀번호 검증까지 간 로그인 1회. 시도 제한(429)에 막힌 요청은 검증 전에 끝나 여기 없다 — HTTP 메트릭 `status="429"`로 본다 |

읽는 법:

- 학습 run 이 꾸준한데 `LEARNED`가 없으면 nights 패널에서 어떤 사유로 빠지는지 본다(예: `INSUFFICIENT_CAFFEINE_RESIDUAL`이
  대부분이면 카페인을 안 마신 밤이 많은 것이고, `MISSING_BEDTIME`이 많으면 앱이 inBed 샘플을 올리지 않는 것이다).
- nights 의 `ALREADY_LEARNED`는 앱이 run 을 다시 부를 때마다 쌓인다. 정상이며, 이 값이 매우 크면 앱의 호출 주기가 잦다는 뜻이다.
- 수면 `duplicate`가 `inserted`보다 계속 크면 앱이 이미 올린 샘플을 반복해 보내고 있다.
- `UNKNOWN_EMAIL`만 크게 늘면 남의 이메일 목록으로 로그인을 시도하는 공격(credential stuffing)을 의심한다.

카운터는 앱 메모리에 있어 재시작하면 0부터 다시 센다. 패널은 `increase()`를 쓰므로 재시작해도 끊김 없이 이어진다.
메트릭은 트랜잭션 커밋 전에 오르므로, 커밋이 실패한 요청(500)도 한 번 세어진다 — 드물고 5xx 패널에 따로 보인다.

화면에서 고친 대시보드는 저장되지 않는다. 바꿀 때는 `monitoring/grafana/dashboards/*.json`을 고쳐 레포에 남기고 EC2로 옮긴다.
장애 경보는 아래 "경보" 절.

대시보드 JSON이나 Prometheus 설정을 바꿨으면 EC2에 올리기 전에 PC에서 먼저 확인한다. `docker-compose.monitoring.yml`이 E2E 앱·DB를
불러와 같은 설정의 Prometheus·Grafana·Alertmanager와 함께 띄운다(포트 18080·19090·13000·19093, 접속 정보는 파일 머리 주석). 요청을 몇 번 보낸 뒤 1~2분 지나야
비율·지연 패널에 값이 나온다. `local` 프로파일 `bootRun`은 메트릭 엔드포인트가 없어 이 용도로 쓸 수 없다.

```bash
# PC: 띄우기 / 내리기
docker compose -f docker-compose.monitoring.yml up --build -d
docker compose -f docker-compose.monitoring.yml down
```

**Alertmanager 켜기 (AWS 준비 후)** — `.env`에 값이 없거나 형식이 틀리면 Alertmanager 컨테이너만 시작을 거부하고 이유를 로그에 남긴다.
앱·Prometheus·Grafana는 영향이 없다.

```bash
# 1. PC: 이미지 저장 후 전송 (compose·monitoring/check.sh 의 태그와 같게)
docker pull --platform linux/amd64 prom/alertmanager:v0.28.1
docker save -o alertmanager-image.tar prom/alertmanager:v0.28.1
scp alertmanager-image.tar <ec2-user>@<ec2-host>:~/

# 2. EC2: .env 에 ALERT_TOPIC_ARN·HEARTBEAT_TOPIC_ARN·AWS_REGION 추가(.env.example 참고) 후 기동
docker load -i alertmanager-image.tar
docker compose -f docker-compose.prod.yml --profile alerting up -d
docker logs caffeine-alertmanager 2>&1 | tail -5   # "Completed loading of configuration file" 이 보여야 한다
```

켠 뒤에는 compose 명령에 `--profile alerting`을 붙인다. 빼면 Alertmanager가 그 명령의 대상에서 빠진다.

**배포 사일런스.** 수동 배포는 앱을 내렸다 올리므로 `AppDown`·`AppRestarted`가 울린다. Alertmanager를 켠 뒤에는 배포 4단계 전에 끈다.
사일런스는 `alertmanager-data` 볼륨에 남아 Alertmanager가 재시작돼도 유지되고, 15분 뒤 저절로 풀린다.

```bash
# EC2: 배포 전 15분 사일런스 / 확인 / 일찍 풀기
docker exec caffeine-alertmanager amtool silence add 'alertname=~"AppDown|AppRestarted"' --duration=15m --comment="수동 배포" --alertmanager.url=http://localhost:9093
docker exec caffeine-alertmanager amtool silence query --alertmanager.url=http://localhost:9093
docker exec caffeine-alertmanager amtool silence expire <ID> --alertmanager.url=http://localhost:9093
```

**경보가 울렸을 때.** 메시지의 "대응" 줄이 이 문서의 어느 절을 볼지 알려 준다. `AppRestarted`가 배포와 무관하게 오면
`docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' caffeine-app`으로 메모리 부족 종료인지 먼저 본다.

**`caffeine-heartbeat-missing`이 울렸을 때.** 서버 다운이 아니라 경보 경로 중 한 곳이 끊긴 것일 수 있다. 하트비트는
Prometheus → Alertmanager → SNS 엔드포인트 → SNS → Lambda → CloudWatch를 모두 지나야 쌓이므로, 위에서부터 차례로 본다.
같은 때 온 다른 메일이 단서가 된다.

| 순서 | 볼 것 | 명령·위치 | 끊겼다면 |
|---|---|---|---|
| 1 | EC2가 살아 있는가 | `caffeine-ec2-status-check` 메일이 같이 왔는가, SSH 접속 | EC2 장애. 인스턴스부터 복구한다 |
| 2 | Alertmanager가 떠 있는가 | EC2: `docker compose -f docker-compose.prod.yml --profile alerting ps` | `docker logs caffeine-alertmanager`의 시작 거부 이유(`.env` 값) |
| 3 | Prometheus가 하트비트를 넘기는가 | EC2: `curl -s localhost:9093/api/v2/alerts \| grep -c Watchdog` (1 이상이어야 한다) | Prometheus 상태(`docker logs caffeine-prometheus`), `alerts.yml` 마운트 |
| 4 | Alertmanager가 SNS로 보내는가 | EC2: `docker logs --since 30m caffeine-alertmanager 2>&1 \| grep -i sns` | 엔드포인트·보안 그룹·IAM·홉 제한 — `경보-AWS-설정.md` 2단계 문제 해결 표 |
| 5 | Lambda가 메트릭을 올리는가 | `caffeine-alert-relay-errors` 메일, `aws logs tail /aws/lambda/caffeine-alert-relay --since 30m` | 역할 정책(`cloudwatch:PutMetricData`), Lambda 오류 |

이메일은 SNS가 직접 보내므로 Lambda·Slack이 고장 나도 온다. **Slack만 조용하면** 5번(Lambda)부터 본다.

## 알려진 함정

- RDS에 초기 DB가 없으면 `Unknown database 'caffeine_tracker'`(1049). `DB_URL` 끝에 `&createDatabaseIfNotExist=true`를 붙이면 해결.
- `docker compose pull`은 EC2에서 쓰지 않는다(인터넷 없음). 갱신은 항상 `docker load`.
- compose는 셸 환경변수를 `.env`보다 우선한다. 배포 셸에 `DB_URL`·`DB_USERNAME`·`DB_PASSWORD`·`JWT_SECRET`이 있으면 그 값이 컨테이너에 들어가므로 `env | grep -E 'DB_|JWT_'`로 먼저 확인한다.
- 컨테이너 healthcheck는 `start_period` 90초 이후부터 판정한다. 기동 직후 unhealthy로 보여도 잠시 기다린다.
- `.env`에 `GRAFANA_ADMIN_PASSWORD`가 없으면 compose가 앱을 포함한 전체 기동을 거부한다(`required variable ... is missing`).
  Grafana 비밀번호는 첫 기동 때만 적용되고 `grafana-data` 볼륨에 남는다. 나중에 바꾸려면
  `docker exec caffeine-grafana grafana cli admin reset-admin-password <새 비밀번호>`.

## 롤백

이전 배포의 tar 파일을 보관해 두면 같은 절차(`docker load` → `up -d`)로 되돌릴 수 있다.
DB `ALTER`는 자동으로 되돌아가지 않으므로 스키마 변경이 포함된 배포는 역방향 `ALTER`를 미리 준비한다.

## 시연 데이터

Apple Watch 없이 학습 대시보드를 보여줄 때 시연 계정에 지난 6밤의 기록을 넣는다. 실제 사용자 계정에는 쓰지 않는다.

```bash
python3 docs/ops/seed_demo.py --base-url <서버 주소> --email <시연 이메일> --password '<비밀번호>'
```

다시 실행할 때는 카페인 기록이 중복되지 않게 `--skip-caffeine`을 붙인다.
