# 운영 가이드 — 수동 배포

> 배포 방식: **수동 배포**. CI(`.github/workflows/ci.yml`)는 빌드+테스트 후 GHCR 이미지 push까지만 자동화한다.
> CD 자동화는 범위 외(수동 유지가 결정 사항). 운영 서버(EC2)·운영 DB(RDS)는 사용자가 직접 관리한다.
> 마지막 갱신: 2026-11-23

## 준비 상태 체크리스트

- [x] Dockerfile
- [x] docker-compose.yml / docker-compose.prod.yml
- [x] CI: 빌드+테스트 → GHCR push (amd64 단일 플랫폼)
- [x] prod 프로파일
- [x] DB DDL (`docs/db/db-schema.sql`, 사용자가 RDS에 직접 적용)
- [x] 운영 서버(EC2) · 운영 DB(RDS) — 사용자 관리 인프라. Terraform으로 만든다: `기반-AWS-설정.md`
- [ ] HTTPS / 리버스 프록시 (iOS ATS 대응)
- [ ] GHCR private 인증 정리

## 배포 전 확인

1. **DB 스키마**: 첫 배포는 RDS에 `docs/db/db-schema.sql` 실행. 이후 스키마 변경은 `docs/db/db-schema.md` 변경 이력의 `ALTER`를
   먼저 적용한다. 앱은 스키마를 만들지 않으므로(`ddl-auto: validate`) 미적용이면 기동 시 `Schema-validation` 실패.
2. **iOS 앱 호환**: 2026-09-03 응답 봉투(`ApiResponse`: success/data/error/message) 도입으로 모든 엔드포인트의 바디 최상위
   구조가 바뀌었다. iOS 앱 디코더가 갱신되기 전에는 운영 배포를 미룬다(계약은 README "공통 응답 구조").
   2026-09-06 `PUT /api/settings`에 `notifications` 객체(cutoff·bedtimeResidual·recordReminder, 전부 필수)가 추가되어
   갱신 전 iOS 빌드의 설정 저장은 400 `VALIDATION_FAILED`를 받는다.
   2026-11-01 리프레시 토큰 JWT 전환으로 배포 시 기존 리프레시 토큰이 모두 무효가 되어 전 사용자가 한 번 다시 로그인한다.
   2026-11-03 로그인에 429 `TOO_MANY_LOGIN_ATTEMPTS`(같은 이메일 15분 내 5회 실패)가 추가됐다. 봉투 구조는 같아 디코딩은
   그대로 되지만, 앱이 로그인 실패를 401로만 가정하면 서버 `message`를 그대로 보여 주는지 확인한다.
3. **CI 통과**: main의 최신 CI가 녹색이고 GHCR에 `latest` 이미지가 올라갔는지 확인.
4. **E2E 통과**: PC에서 `./gradlew e2eTest`. 운영과 같은 `prod` 프로파일·실제 MySQL·실제 이미지로 가입→학습→로그아웃을 돌린다.
   H2 통합 테스트가 못 잡는 문자셋·collation·DDL 문제와, 같은 사용자 동시 쓰기(학습 실행·수면 업로드)의 잠금 순서 위반
   (MySQL REPEATABLE READ 에서만 500)이 여기서 드러난다(Docker 필요, 수 분 소요).

## 수동 배포 절차

EC2는 외부 인터넷이 없어 `docker compose pull`이 불가하다. PC에서 이미지를 받아 파일로 옮긴다.

```bash
# 1. PC: GHCR 로그인 (이미지가 private)
gh auth refresh -s read:packages
gh auth token | docker login ghcr.io -u ksiksit --password-stdin

# 2. PC: 이미지 pull + 파일로 저장 (CI는 amd64만 빌드 — Apple Silicon에서는 pull·save 둘 다 platform 명시.
#    save 에서 빼면 "unable to create manifests file: NotFound: content digest ..." 로 실패한다 — 받지 않은 arm 쪽까지 저장하려 해서다)
docker pull --platform linux/amd64 ghcr.io/ksiksit/caffeine_tracker_server:latest
docker save --platform linux/amd64 -o caffeine-app.tar ghcr.io/ksiksit/caffeine_tracker_server:latest

# 3. PC → EC2 전송
scp caffeine-app.tar <ec2-user>@<ec2-host>:~/

# 4. EC2: 이미지 로드 후 기동 (Alertmanager 를 켰다면 먼저 배포 사일런스 — "경보" 절)
docker load -i caffeine-app.tar
docker compose -f docker-compose.prod.yml up -d

# 5. EC2: 헬스 확인
curl localhost:8081/actuator/health   # {"status":"UP"} 이면 성공

# 6. PC: 스모크 E2E — SSH 터널로 EC2:8080 을 PC:18081 로 연결한 뒤 읽기 위주 시나리오 실행
ssh -N -L 18081:localhost:8080 <ec2-user>@<ec2-host> &
E2E_EMAIL=<전용 계정> E2E_PASSWORD=<비밀번호> ./gradlew e2eTest -Pe2e.baseUrl=http://localhost:18081
kill %1   # 터널 종료
```

스모크 전용 계정은 운영에 한 번만 가입 API로 만들어 두고, 자격증명은 레포·스크립트에 저장하지 않는다.
`-Pe2e.baseUrl`이 있으면 쓰기 시나리오(가입·기록·학습)는 건너뛰고 로그인·조회·토큰 재발급만 확인한다. 터널은 API 포트만 연결하므로 헬스는 5단계에서 확인한다.

EC2 홈(`~`)에 `docker-compose.prod.yml`, `monitoring/` 폴더, `.env`(`DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`,
`GRAFANA_ADMIN_PASSWORD`)를 같은 폴더에 둔다. compose가 같은 폴더의 `.env`를 자동 로드하고, `monitoring/`의 설정 파일을
상대 경로로 마운트한다. 위 절차는 앱 이미지만 옮긴다 — Prometheus·Grafana를 처음 올리거나 버전·설정을 바꿀 때는
아래 "Prometheus·Grafana 설치" 절차를 먼저 한다. 이미지가 EC2에 없으면 `up -d`가 pull을 시도하다 실패한다.

## 쓸 때만 켜기 (EC2·RDS)

EC2와 RDS는 24시간 켜 두지 않는다. **쓰는 날 켜고, 그날 쓰임이 끝나면 끈다.** 구조(Terraform 자원)는 그대로 두고 가동 시간만 줄인다.
끄고 켜는 일은 PC에서 `infra/scripts/power.sh`로 한다(AWS CLI와 관리자 자격 증명 필요. 자원을 이름으로 찾으므로 Terraform state는 없어도 된다).

| 명령 | 하는 일 | 걸리는 시간 |
|---|---|---|
| `bash infra/scripts/power.sh status` | EC2·RDS 상태, 알람별 알림 켜짐 여부, 판정 한 줄. 아무것도 바꾸지 않는다 | 몇 초 |
| `bash infra/scripts/power.sh up` | RDS 시작·available 대기 → EC2 시작 → 8080 응답 확인(최대 5분) → 경보 알림 켬 | 10~15분 |
| `bash infra/scripts/power.sh down` | 경보 알림 멈춤 → EC2 정지(기다림) → RDS 정지 요청 | 1~2분 (RDS는 그 뒤 몇 분 더) |

**켜는 때**: 시연·발표, iOS 앱을 서버에 붙여 하는 테스트, 배포와 스모크 E2E, 운영 DB 작업(스키마 `ALTER` 등).
**끄는 때**: 그 일이 끝난 날. 다음 날도 쓸 거면 밤새 켜 둬도 된다(하룻밤 16시간에 약 $0.8).
**꺼 둔 동안 앱은 서버에 닿지 못한다** — 로그인·기록·조회 등 모든 요청이 연결 실패로 끝난다. 앱을 쓰는 사람이 있으면 끄기 전에 알린다.

### 켜기 (시연·테스트 전)

`up`이 10~15분 걸리고 그 뒤 확인이 있으므로 **쓰기 30분 전**에 시작한다. 고정 IP라 서버 주소는 꺼졌다 켜져도 같다.

```bash
# 1. PC: 지금 상태. 꺼 둔 상태면 "판정: 꺼짐", RDS 만 저절로 켜졌으면 "주의: EC2 는 멈췄는데 RDS 가 켜져 있다" (어느 쪽이든 up 으로 넘어간다)
bash infra/scripts/power.sh status

# 2. PC: 켜기. 아래 줄이 차례로 나오고 "완료." 로 끝나야 한다
bash infra/scripts/power.sh up
#   - RDS 시작 요청, available 까지 기다린다 (보통 5~10분)
#   - RDS available
#   - EC2 시작 요청
#   - EC2 running
#   - 앱 응답 기다림: http://<고정 IP>:8080 (최대 300초)
#   - 앱 응답 HTTP 401          ← 인증 없이 불렀으므로 401 이 정상이다
#   - 경보 알림 켬: 6개          ← 알람 수는 Terraform 설정에 따라 다르다
```

`up`이 "앱이 300초 안에 응답하지 않았다"로 끝나면 경보 알림은 멈춘 채다. SSH로 들어가 `docker ps`와 `docker logs caffeine-app`를 보고
고친 뒤 `up`을 다시 실행한다(이미 켜진 것은 건너뛰고 응답 확인과 알림 켜기만 다시 한다).

**켠 뒤 확인.** `up`은 8080이 응답하는 것까지만 본다. 아래를 차례로 확인한다.

| 순서 | 볼 것 | 명령 | 기대 결과 |
|---|---|---|---|
| 1 | 전체 상태 | PC: `bash infra/scripts/power.sh status` | `EC2 ...: running`, `RDS caffeine-db: available`, 모든 알람의 둘째 칸이 `True`, 마지막 줄 `판정: 켜짐` |
| 2 | 앱과 DB | EC2: `curl localhost:8081/actuator/health` | `{"status":"UP"}` — DB 연결이 끊겨 있으면 `DOWN`이다 |
| 3 | 컨테이너 | EC2: `docker compose -f docker-compose.prod.yml --profile alerting ps` | app·prometheus·alertmanager·grafana가 모두 `Up` (부팅 때 저절로 다시 뜬다) |
| 4 | 경보 경로 | EC2: `curl -s localhost:9093/api/v2/alerts \| grep -c Watchdog` | 1 이상 (부팅 후 1~2분 걸린다) |
| 5 | 하트비트 알람 | PC: `up`이 끝나고 15분쯤 뒤 `bash infra/scripts/power.sh status` | `caffeine-heartbeat-missing`의 셋째 칸이 `OK`. 이때 "해제" 메일·Discord가 한 통 온다 |
| 6 | 실제 요청 (시연 전) | 앱으로 로그인하거나 "수동 배포 절차" 6단계의 스모크 E2E | 로그인 성공 |

5번을 건너뛰지 않는다. 알림은 알람 **상태가 바뀔 때만** 가므로, 하트비트 알람이 `ALARM`인 채로 남으면(Alertmanager가 뜨지 않은 경우)
알림을 켜 두어도 아무것도 오지 않는다. 20분이 지나도 `ALARM`이면 "경보" 절의 "`caffeine-heartbeat-missing`이 울렸을 때" 표를 2번부터 본다.
켠 직후 앱이 늦게 뜨면 `AppDown`과 그 해제 알림이 한 번 올 수 있다(Alertmanager가 보내는 것이라 `power.sh`가 멈추는 대상이 아니다).

### 끄기

```bash
# 1. PC: 끄기 전 상태. "판정: 켜짐" 이어야 한다. "전환 중" 이면 기다렸다 다시 본다
bash infra/scripts/power.sh status

# 2. PC: 끄기
bash infra/scripts/power.sh down
#   - 경보 알림 멈춤: 6개
#   - EC2 정지 요청, 멈출 때까지 기다린다
#   - EC2 stopped
#   - RDS 정지 요청 (멈추기까지 몇 분 걸린다. 끝까지 기다리지 않는다)

# 3. PC: 5~10분 뒤 확인. "판정: 꺼짐" 과 "AWS 가 RDS 를 다시 켜는 시각" 이 나와야 한다
bash infra/scripts/power.sh status
```

**끄기 전 확인.**

- 서버를 쓰는 사람이 없다(시연·테스트가 끝났다). 끄면 앱의 모든 요청이 실패한다.
- 배포나 DB 작업(`ALTER`, 시연 데이터 넣기)이 진행 중이 아니다.
- 필요한 로그는 미리 본다. 컨테이너 로그와 Prometheus 데이터는 디스크에 남지만, 꺼 둔 동안의 메트릭은 비어 있다.

3단계 `status`가 알려 주는 "다시 켜는 시각"(UTC)을 달력에 적어 둔다 — 아래 "RDS는 7일 뒤 저절로 켜진다".
RDS가 `stopping`인 동안에는 그 시각이 아직 나오지 않을 수 있다. `down`은 여러 번 실행해도 된다(이미 멈춘 것은 건너뛴다).

### 경보와 함께 꺼지는 것

`power.sh`는 이름이 `caffeine-`으로 시작하는 CloudWatch 알람 전부의 **알림 동작**을 멈추고 켠다(알람 자체는 남고 상태도 계속 바뀐다).
지금 Terraform이 만드는 알람은 전부 이 접두사다: `caffeine-ec2-status-check`, `caffeine-ec2-cpu-credit`, `caffeine-ec2-auto-recover`(선택),
`caffeine-rds-free-storage`, `caffeine-rds-cpu`, `caffeine-alert-relay-errors`, `caffeine-heartbeat-missing`(선택).
**알람을 새로 만들 때는 이름을 `caffeine-`으로 시작하고 `ap-northeast-2`에 둔다.** 다른 리전에 두어야 하는 알람(예: Route 53 헬스 체크 지표는
`us-east-1`에만 있다)은 `power.sh`가 찾지 못하므로 스크립트도 같이 고친다.

꺼 둔 동안 알람 상태는 이렇게 보이는 것이 정상이다: 하트비트 `ALARM`(데이터가 없으면 경보로 본다), EC2·RDS 알람 `INSUFFICIENT_DATA`, Lambda 오류 알람 `OK`.
Prometheus 규칙(`AppDown` 등)은 EC2 안에서 돌므로 EC2가 멈추면 함께 멈춘다.

| 순서·처리 | 이유 |
|---|---|
| `down`은 경보 알림부터 멈춘다 | 그냥 멈추면 15분쯤 뒤 하트비트 알람이 메일·Discord로 온다 |
| `up`은 RDS를 먼저 켠다 | EC2가 먼저 뜨면 앱이 DB에 붙지 못해 재시작을 되풀이한다 |
| 앱은 따로 올리지 않는다 | 부팅 때 Docker가 켜지고 컨테이너가 `restart: unless-stopped`로 다시 뜬다 |
| `up`은 앱이 응답한 뒤에만 알림을 켠다 | 뜨지 않은 서버의 경보가 쏟아지지 않게 한다. 대신 실패하면 알림이 멈춘 채이므로 고치고 `up`을 다시 실행한다 |

### 꺼 둔 동안 `terraform apply`를 했다면

Terraform은 알람의 `actions_enabled`를 `true`로 관리한다. `power.sh`가 멈춰 둔 알림은 Terraform이 보기에 어긋난 값이라,
꺼 둔 동안의 `terraform plan`에는 알람마다 `actions_enabled: false -> true`가 나오고 **`apply`를 하면 알림이 다시 켜진다.**
그대로 두면 켜질 때까지 조용하다가(상태가 바뀌지 않으므로) RDS가 저절로 켜지는 등 상태가 바뀌는 순간부터 알림이 온다.

- 꺼 둔 동안에는 되도록 `apply`를 하지 않는다. 켠 뒤에 한다.
- 꺼 둔 동안 `apply`를 했으면 **바로 `bash infra/scripts/power.sh down`을 다시 실행**한다. EC2·RDS는 이미 멈춰 있어 건너뛰고 알림만 다시 멈춘다.
  이어서 `status`가 `판정: 꺼짐`인지 본다 — 알림이 켜진 알람이 남아 있으면 `주의: 꺼 둔 상태인데 알림이 켜진 알람이 N개다`가 나온다.
- 켜 둔 동안에는 값이 같으므로(`true`) `plan`에 이 차이가 나오지 않는다. 켜 둔 상태에서 나오면 `up`이 끝까지 가지 못한 것이다 — `status`로 본다.
- 멈춘 RDS는 설정을 바꿀 수 없다. RDS를 고치는 `apply`(인스턴스 크기·비밀번호 등)는 켠 뒤에 한다.

### RDS는 7일 뒤 저절로 켜진다

AWS는 멈춘 RDS를 7일 뒤 자동으로 다시 켠다(끌 수 없는 동작이다). EC2는 멈춘 채이고 알림도 멈춰 있어 **아무 알림 없이 RDS 요금(하루 약 $0.6)이 나가기 시작한다.**

- `down` 뒤 `status`가 알려 준 "다시 켜는 시각" 다음 날에 `bash infra/scripts/power.sh status`를 실행한다. 달력에 반복 일정으로 넣어 둔다.
- `주의: EC2 는 멈췄는데 RDS 가 켜져 있다`가 나오면 `bash infra/scripts/power.sh down`을 다시 실행하고, 5~10분 뒤 `status`로 새 "다시 켜는 시각"을 적는다.
- 언제 켜졌는지는 RDS 이벤트로 본다(최근 14일):
  `aws rds describe-events --region ap-northeast-2 --source-type db-instance --source-identifier caffeine-db --duration 20160 --query 'Events[].[Date,Message]' --output text`
  — `DB instance is being started due to it exceeding the maximum allowed time being stopped.` 줄이 그것이다.
- 2주 넘게 안 쓸 거면 매주 다시 끄는 대신 `기반-AWS-설정.md` "되돌리기"로 지우는 쪽을 검토한다.

자동으로 다시 끄는 장치(스케줄러·Lambda)는 아직 두지 않았다. 지금은 위의 수동 점검이 전부다.

### 비용 (서울 리전 정가 기준 추정, 한 달 730시간)

| 항목 | 켜 둔 동안 | 꺼 둔 동안 |
|---|---|---|
| EC2 `t3.small` ($0.026/시간) | 월 약 $19 | $0 |
| RDS `db.t4g.micro` ($0.025/시간) | 월 약 $18 | $0 |
| EC2 디스크 20GB + RDS 저장공간 20GB | 월 약 $4.4 | 같다 |
| 고정 IP (공인 IPv4, $0.005/시간) | 월 약 $3.7 | 같다 |
| 경보의 SNS 엔드포인트 ($0.013/시간, `alerting_enabled`일 때) | 월 약 $9.5 | 같다 |

- 하루 8시간만 켜면 EC2·RDS 요금이 월 약 $37에서 약 $12로 줄어 **월 약 $25**를 아낀다.
- **꺼 둔 동안에도 나가는 돈**: 디스크와 고정 IP 월 약 $8, 경보를 켜 두었으면 엔드포인트 월 약 $9.5가 더해져 월 약 $18.
  엔드포인트까지 줄이려면 `terraform.tfvars`에 `alerting_enabled = false`를 넣고 apply한다(경보 자원이 지워지고, 다시 켜면 `경보-AWS-설정.md`의 확인을 다시 한다).

## 메트릭과 로그

운영 프로파일에서 헬스·메트릭은 관리 포트 8081에서만 응답하고 8080에서는 404다. compose는 8081을 EC2 루프백에만
바인딩하므로 EC2 안에서 조회한다. 보안 그룹이나 compose에서 8081을 외부로 열지 않는다 — 인증 없이 응답하는 포트다.

```bash
# EC2: Prometheus 형식 메트릭 (HTTP 요청, JVM, Hikari 등)
curl localhost:8081/actuator/prometheus

# EC2: 5xx 요청 찾기. 로그는 JSON 한 줄이고 requestId·userId 필드가 함께 나간다
docker logs caffeine-app 2>&1 | grep 'status=5'

# EC2: 한 요청의 로그 전부 보기
docker logs caffeine-app 2>&1 | grep '<requestId>'
```

로그는 컨테이너당 10MB × 5개까지만 보관하므로 오래된 로그는 사라진다.

### Prometheus·Grafana

`docker-compose.prod.yml`이 앱과 함께 Prometheus와 Grafana를 띄운다. Prometheus가 `app:8081/actuator/prometheus`를
15초마다 긁어 15일(또는 2GB)까지 쌓고, Grafana가 "카페인 트래커 서버" 대시보드로 보여 준다. 데이터소스와 대시보드는
`monitoring/grafana/`에서 기동 때 자동 등록된다. 두 포트(9090·3000)도 인증이 약하거나 없으므로 루프백에만 바인딩하고
PC에서는 SSH 터널로 본다.

```bash
# PC: Grafana(3000)·Prometheus(9090) 터널. 브라우저로 http://localhost:3000 → admin / GRAFANA_ADMIN_PASSWORD
ssh -N -L 3000:localhost:3000 -L 9090:localhost:9090 <ec2-user>@<ec2-host>

# EC2: 수집 대상 상태 — "health":"up" 이면 앱 메트릭을 긁고 있다
curl -s localhost:9090/api/v1/targets | grep -o '"health":"[a-z]*"'
```

대시보드 패널: 수집 상태·5xx 비율·p95 지연·초당 요청(상단), 엔드포인트별 요청·p95, 상태 코드별 요청, ERROR·WARN 로그 수,
JVM 힙, DB 커넥션 풀, CPU, 그리고 아래 도메인 메트릭 4개(학습 실행·학습 밤별·수면 업로드·로그인, 최근 1시간 합계).
5xx나 지연이 튀면 그 시각의 로그를 `docker logs --since`로 보고 `requestId`로 좁힌다.
p95는 `application-prod.yaml`의 지연 버킷(25ms~5s 8개) 사이를 보간한 근삿값이다.

#### 도메인 메트릭

HTTP 메트릭은 상태 코드까지만 보인다. 학습 run 은 건너뛰어도 200, 수면 업로드는 중복이 섞여도 200, 로그인 실패는 이메일이
없든 비밀번호가 틀리든 같은 401 이라, 서비스가 실제로 한 일은 아래 카운터로 본다. 모두 기동 때 0으로 등록되고,
사용자 식별자는 태그로 붙이지 않는다(사용자 수만큼 시계열이 늘어난다). 메트릭은 관리 포트(8081)에서만 나간다.

| 메트릭 (Prometheus 이름) | 태그 | 1 오르는 때 |
|---|---|---|
| `caffeine_learning_runs_total` | `outcome` = `LEARNED` 또는 skip 사유 | 학습 실행 1회. 1밤 이상 학습했으면 `LEARNED`, 아니면 응답 `skipReason`과 같은 값 |
| `caffeine_learning_nights_total` | `outcome` = `LEARNED` 또는 밤 단위 skip 사유 | 실행이 살펴본 후보 밤 1개. `LEARNING_DISABLED`·`NO_SLEEP_SUMMARY`는 실행 전체 사유라 여기 없다 |
| `caffeine_sleep_samples_total` | `result` = `inserted`·`duplicate` | 업로드된 샘플 1개. `duplicate` = 이미 저장됐거나 같은 배치 안에서 겹친 샘플(응답 `received - inserted`) |
| `caffeine_auth_logins_total` | `outcome` = `SUCCESS`·`WRONG_PASSWORD`·`UNKNOWN_EMAIL` | 비밀번호 검증까지 간 로그인 1회. 시도 제한(429)에 막힌 요청은 검증 전에 끝나 여기 없다 — HTTP 메트릭 `status="429"`로 본다 |

읽는 법:

- 학습 run 이 꾸준한데 `LEARNED`가 없으면 nights 패널에서 어떤 사유로 빠지는지 본다(예: `INSUFFICIENT_CAFFEINE_RESIDUAL`이
  대부분이면 카페인을 안 마신 밤이 많은 것이고, `MISSING_BEDTIME`이 많으면 앱이 inBed 샘플을 올리지 않는 것이다).
- nights 의 `ALREADY_LEARNED`는 앱이 run 을 다시 부를 때마다 쌓인다. 정상이며, 이 값이 매우 크면 앱의 호출 주기가 잦다는 뜻이다.
- 수면 `duplicate`가 `inserted`보다 계속 크면 앱이 이미 올린 샘플을 반복해 보내고 있다.
- `UNKNOWN_EMAIL`만 크게 늘면 남의 이메일 목록으로 로그인을 시도하는 공격(credential stuffing)을 의심한다.

카운터는 앱 메모리에 있어 재시작하면 0부터 다시 센다. 패널은 `increase()`를 쓰므로 재시작해도 끊김 없이 이어진다.
메트릭은 트랜잭션 커밋 전에 오르므로, 커밋이 실패한 요청(500)도 한 번 세어진다 — 드물고 5xx 패널에 따로 보인다.

화면에서 고친 대시보드는 저장되지 않는다. 바꿀 때는 `monitoring/grafana/dashboards/*.json`을 고쳐 레포에 남기고 EC2로 옮긴다.
장애 경보는 아래 "경보" 절.

대시보드 JSON이나 Prometheus 설정을 바꿨으면 EC2에 올리기 전에 PC에서 먼저 확인한다. `docker-compose.monitoring.yml`이 E2E 앱·DB를
불러와 같은 설정의 Prometheus·Grafana·Alertmanager와 함께 띄운다(포트 18080·19090·13000·19093, 접속 정보는 파일 머리 주석). 요청을 몇 번 보낸 뒤 1~2분 지나야
비율·지연 패널에 값이 나온다. `local` 프로파일 `bootRun`은 메트릭 엔드포인트가 없어 이 용도로 쓸 수 없다.

```bash
# PC: 띄우기 / 내리기
docker compose -f docker-compose.monitoring.yml up --build -d
docker compose -f docker-compose.monitoring.yml down
```

#### Prometheus·Grafana 설치 (처음 한 번, 버전·설정을 바꿀 때)

```bash
# 1. PC: 이미지 저장 (compose 의 태그와 같게)

docker pull --platform linux/amd64 grafana/grafana:12.1.0
docker save --platform linux/amd64 -o monitoring-images.tar prom/prometheus:v3.5.0 grafana/grafana:12.1.0

# 2. PC → EC2: 이미지, compose, 설정 폴더
scp monitoring-images.tar docker-compose.prod.yml <ec2-user>@<ec2-host>:~/
scp -r monitoring <ec2-user>@<ec2-host>:~/

# 3. EC2: .env 에 GRAFANA_ADMIN_PASSWORD 추가(openssl rand -base64 24), 여유 확인 후 기동
free -h && df -h ~            # 두 컨테이너가 합쳐 수백 MB 메모리, 디스크는 최대 2GB 남짓 더 쓴다
```

### 경보

설계와 남은 단계: `../alerting-plan.md`. **2026-11-10 운영에 전부 반영했다**(규칙 평가, Alertmanager → SNS → 이메일·메신저, 하트비트 알람).
메신저 전달은 Lambda `caffeine-alert-relay`가 Discord 웹훅으로 한다(2026-11-22에 Slack에서 바꿨다. 이메일 직접 구독은 그대로다).
서버를 새로 만들었을 때는 Alertmanager를 AWS 준비(SNS 토픽·VPC 엔드포인트·인스턴스 역할, 설계 §11 1~2단계)와 그 확인 뒤에 켠다.
AWS 자원은 Terraform이 만든다(`기반-AWS-설정.md`). 준비와 단계별 확인: `경보-AWS-설정.md`.

- **규칙**: `monitoring/prometheus/alerts.yml` 12개(앱 다운·재시작, 5xx, p95 지연, DB 커넥션, 힙, ERROR 로그, 디스크 2단계, 로그인 공격 의심,
  하트비트). Prometheus가 15초마다 평가한다. 임계값과 이유는 파일 주석과 설계 §3.
- **지금 울리는 경보 보기**: 위 터널을 연 뒤 `http://localhost:9090/alerts`. EC2에서는 `curl -s localhost:9090/api/v1/alerts`.
  `Watchdog`은 늘 울린다 — 경보 경로 하트비트이므로 정상이다.
- **처음 반영할 때**: 앱 배포와 별개로 `docker-compose.prod.yml`과 `monitoring/` 폴더를 EC2에 올리고 `docker compose -f docker-compose.prod.yml up -d`.
  Prometheus가 `alerts.yml` 마운트를 받아 다시 만들어진다. Alertmanager는 `alerting` 프로필 뒤에 있어 이때 뜨지 않는다.
- **Alertmanager가 없는 동안** Prometheus 로그에 `alertmanager:9093` 연결 실패가 주기적으로 남는다. 무해하다.

규칙이나 Alertmanager 설정을 바꿀 때는 `alerts.test.yml`의 경계값 테스트도 같이 고치고 PC에서 검사한다. CI도 같은 스크립트를 돌린다.
메트릭 이름·라벨이 규칙과 어긋나면 `AlertRuleMetricsIT`가 빌드를 실패시킨다.

```bash
# PC: 규칙 문법·경계값 테스트·Alertmanager 설정·라우팅·메시지 템플릿 검사 (promtool·amtool 이 없으면 Docker 이미지로 실행)
sh monitoring/check.sh

# PC: 로컬에서 실제로 울려 보기 — 앱을 내리면 2~3분 뒤 AppDown 이 alert-sink 로그에 찍히고, start app 으로 올리면 resolved 가 찍힌다
docker compose -f docker-compose.monitoring.yml up --build -d
docker compose -f docker-compose.monitoring.yml stop app
docker compose -f docker-compose.monitoring.yml logs -f alert-sink
```

**Alertmanager 켜기 (AWS 준비 후)** — `.env`에 값이 없거나 형식이 틀리면 Alertmanager 컨테이너만 시작을 거부하고 이유를 로그에 남긴다.
앱·Prometheus·Grafana는 영향이 없다.

```bash
# 1. PC: 이미지 저장 후 전송 (compose·monitoring/check.sh 의 태그와 같게)
docker pull --platform linux/amd64 prom/alertmanager:v0.28.1
docker save --platform linux/amd64 -o alertmanager-image.tar prom/alertmanager:v0.28.1
scp alertmanager-image.tar <ec2-user>@<ec2-host>:~/

# 2. EC2: .env 에 ALERT_TOPIC_ARN·HEARTBEAT_TOPIC_ARN·AWS_REGION 추가(.env.example 참고) 후 기동
docker load -i alertmanager-image.tar
docker compose -f docker-compose.prod.yml --profile alerting up -d
docker logs caffeine-alertmanager 2>&1 | tail -5   # "Completed loading of configuration file" 이 보여야 한다
```

켠 뒤에는 compose 명령에 `--profile alerting`을 붙인다. 빼면 Alertmanager가 그 명령의 대상에서 빠진다.

**배포 사일런스.** 수동 배포는 앱을 내렸다 올리므로 `AppDown`·`AppRestarted`가 울린다. Alertmanager를 켠 뒤에는 배포 4단계 전에 끈다.
사일런스는 `alertmanager-data` 볼륨에 남아 Alertmanager가 재시작돼도 유지되고, 15분 뒤 저절로 풀린다.

```bash
# EC2: 배포 전 15분 사일런스 / 확인 / 일찍 풀기
docker exec caffeine-alertmanager amtool silence add 'alertname=~"AppDown|AppRestarted"' --duration=15m --comment="수동 배포" --alertmanager.url=http://localhost:9093
docker exec caffeine-alertmanager amtool silence query --alertmanager.url=http://localhost:9093
docker exec caffeine-alertmanager amtool silence expire <ID> --alertmanager.url=http://localhost:9093
```

**경보가 울렸을 때.** 메시지의 "대응" 줄이 이 문서의 어느 절을 볼지 알려 준다. `AppRestarted`가 배포와 무관하게 오면
`docker inspect -f '{{.State.OOMKilled}} {{.RestartCount}}' caffeine-app`으로 메모리 부족 종료인지 먼저 본다.

**`caffeine-heartbeat-missing`이 울렸을 때.** 서버 다운이 아니라 경보 경로 중 한 곳이 끊긴 것일 수 있다. 하트비트는
Prometheus → Alertmanager → SNS 엔드포인트 → SNS → Lambda → CloudWatch를 모두 지나야 쌓이므로, 위에서부터 차례로 본다.
같은 때 온 다른 메일이 단서가 된다.

| 순서 | 볼 것 | 명령·위치 | 끊겼다면 |
|---|---|---|---|
| 1 | EC2가 살아 있는가 | `caffeine-ec2-status-check` 메일이 같이 왔는가, SSH 접속 | EC2 장애. 인스턴스부터 복구한다 |
| 2 | Alertmanager가 떠 있는가 | EC2: `docker compose -f docker-compose.prod.yml --profile alerting ps` | `docker logs caffeine-alertmanager`의 시작 거부 이유(`.env` 값) |
| 3 | Prometheus가 하트비트를 넘기는가 | EC2: `curl -s localhost:9093/api/v2/alerts \| grep -c Watchdog` (1 이상이어야 한다) | Prometheus 상태(`docker logs caffeine-prometheus`), `alerts.yml` 마운트 |
| 4 | Alertmanager가 SNS로 보내는가 | EC2: `docker logs --since 30m caffeine-alertmanager 2>&1 \| grep -i sns` | 엔드포인트·보안 그룹·IAM·홉 제한 — `경보-AWS-설정.md` "2단계 확인"의 문제 해결 표 |
| 5 | Lambda가 메트릭을 올리는가 | `caffeine-alert-relay-errors` 메일, `aws logs tail /aws/lambda/caffeine-alert-relay --since 30m` | 역할 정책(`cloudwatch:PutMetricData`), Lambda 오류 |

이메일은 SNS가 직접 보내므로 Lambda·Discord가 고장 나도 온다. **Discord만 조용하면** 5번(Lambda)부터 본다 — 웹훅 쪽 원인은 `경보-AWS-설정.md` "4단계 확인"의 문제 해결 표.

## 알려진 함정

- RDS에 초기 DB가 없으면 `Unknown database 'caffeine_tracker'`(1049). `DB_URL` 끝에 `&createDatabaseIfNotExist=true`를 붙이면 해결.
- `docker compose pull`은 EC2에서 쓰지 않는다(인터넷 없음). 갱신은 항상 `docker load`.
- compose는 셸 환경변수를 `.env`보다 우선한다. 배포 셸에 `DB_URL`·`DB_USERNAME`·`DB_PASSWORD`·`JWT_SECRET`이 있으면 그 값이 컨테이너에 들어가므로 `env | grep -E 'DB_|JWT_'`로 먼저 확인한다.
- 컨테이너 healthcheck는 `start_period` 90초 이후부터 판정한다. 기동 직후 unhealthy로 보여도 잠시 기다린다.
- `.env`에 `GRAFANA_ADMIN_PASSWORD`가 없으면 compose가 앱을 포함한 전체 기동을 거부한다(`required variable ... is missing`).
  Grafana 비밀번호는 첫 기동 때만 적용되고 `grafana-data` 볼륨에 남는다. 나중에 바꾸려면
  `docker exec caffeine-grafana grafana cli admin reset-admin-password <새 비밀번호>`.

## 롤백

이전 배포의 tar 파일을 보관해 두면 같은 절차(`docker load` → `up -d`)로 되돌릴 수 있다.
DB `ALTER`는 자동으로 되돌아가지 않으므로 스키마 변경이 포함된 배포는 역방향 `ALTER`를 미리 준비한다.

Apple Watch 없이 학습 대시보드를 보여줄 때 시연 계정에 지난 6밤의 기록을 넣는다. 실제 사용자 계정에는 쓰지 않는다.

```bash
python3 docs/ops/seed_demo.py --base-url <서버 주소> --email <시연 이메일> --password '<비밀번호>'
```

다시 실행할 때는 카페인 기록이 중복되지 않게 `--skip-caffeine`을 붙인다.
